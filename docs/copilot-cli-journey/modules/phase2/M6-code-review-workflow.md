# M6: 代码审查加速

## 概览

代码审查（Code Review）是团队质量保障的关键环节，但传统的 Review 方式依赖审查者记忆力和经验，很容易遗漏问题。Copilot CLI 可以作为**审查前的第一道 AI 检查**，帮助你快速生成 PR 描述、自动扫描常见问题，并给出结构化的审查建议。本模块专注于将 Copilot 集成到 Git 工作流中，提升 Review 效率。

---

## 核心概念 (理论 ~ 30-40%)

### 概念 1: Copilot 在代码审查中的定位

Copilot CLI **不是**替代人工审查，而是：

| 场景 | Copilot 的作用 | 人工的作用 |
|------|--------------|----------|
| PR 描述生成 | ✅ 自动从 diff 提取关键信息 | 补充业务背景 |
| 通用问题扫描 | ✅ 识别常见模式问题 | 判断业务逻辑正确性 |
| 审查注释辅助 | ✅ 生成标准化格式的注释 | 决策接受或拒绝 |
| 最终决策 | ❌ 不能替代 | ✅ 人工负责 |

**最佳实践**：用 Copilot 做**审查前的自动化检查**，减少低级错误，让人工 Review 聚焦在业务逻辑和架构决策上。

### 概念 2: 代码审查的常见检查维度

有效的代码审查覆盖以下维度，可以分别用 Copilot 生成对应的检查提示：

| 维度 | 典型检查点 | 提示关键词 |
|------|----------|----------|
| **功能正确性** | 逻辑是否符合需求 | "是否有 bug 或逻辑错误" |
| **代码可读性** | 命名、注释、结构 | "命名是否清晰" |
| **安全性** | 注入、暴露信息 | "是否有安全漏洞" |
| **性能** | 循环、查询、内存 | "是否有性能问题" |
| **测试覆盖** | 新功能是否有对应测试 | "是否需要补充测试" |
| **文档完整性** | Docstring、README | "文档是否完整" |

### 概念 3: 结构化 PR 描述的价值

好的 PR 描述应该包含：
1. **变更目的** — 为什么做这个改动
2. **变更内容** — 改动了哪些部分
3. **测试验证** — 如何验证改动有效
4. **潜在影响** — 是否影响其他功能

手动写这些内容耗时且容易遗漏，Copilot CLI 可以从 diff 自动提取并结构化输出。

## 实战应用 (70% 以上)

### 场景 1: 从 Git Diff 生成 PR 描述

**问题描述**

你完成了一个功能，但是写 PR 描述总是忘记要点，或者写得太简短，Review 者看不懂改动的意图。

**Copilot CLI 解决方案**

```bash
# 方式 1：为当前 branch 相对 main 的改动生成 PR 描述
git diff main...HEAD | gh copilot suggest "根据以上 Git diff，生成结构化的 PR 描述，包含：
- 变更目的（1-2 句话）
- 主要改动（bullet list，按文件/功能分组）
- 如何测试（测试步骤或测试命令）
- 潜在影响（是否影响其他功能，需要特别注意的地方）
使用 Markdown 格式"

# 方式 2：只看 staged changes
git diff --staged | gh copilot suggest "用中文生成 PR 描述"
```

**结果与验证**

生成的 PR 描述示例：
```markdown
## 变更目的
修复用户登录后 MFA 跳过验证的安全漏洞（issue #142）

## 主要改动
- `src/auth/validator.py`：修复 `validate_token()` 的逻辑错误，确保 MFA 检查在 session 刷新后也生效
- `tests/test_validator.py`：新增 3 个 MFA bypass 场景的回归测试
- `src/auth/models.py`：为 `mfa_enabled` 字段添加默认值 `False`

## 如何测试
1. `pytest tests/test_validator.py -v`
2. 手动测试：登录后修改 session 并尝试跳过 MFA

## 潜在影响
- 影响所有启用 MFA 的用户的登录流程
- 需要通知 QA 团队重新验证登录场景
```

**常见陷阱与对策**

- ❌ 陷阱 1：diff 太大，Copilot 遗漏关键改动
  - ✅ 对策：把大 PR 拆成小 PR，或分模块生成描述后合并
- ❌ 陷阱 2：生成的描述包含太多代码细节，不够清晰
  - ✅ 对策：在提示中要求"面向非技术人员描述目的，技术细节只在必要时提及"

### 场景 2: 自动生成审查建议

**问题描述**

你需要审查同事提交的代码，但担心遗漏潜在问题，希望先用 Copilot 做一遍初步扫描。

**Copilot CLI 解决方案**

```bash
# 分析特定文件的变更
git show HEAD:src/payments/processor.py | gh copilot suggest "请对以下代码进行审查，找出：
1. 潜在的 bug 或逻辑错误
2. 安全问题（特别是金融相关的业务逻辑）
3. 错误处理不足的地方
4. 可读性问题（命名、注释）
对每个问题给出：问题位置、问题描述、建议改进方式。
用 Markdown bullet list 格式输出。"
```

**结果与验证**

生成后，人工检查每条建议是否合理，然后决定哪些需要在 Review 中提出。

**常见陷阱与对策**

- ❌ 陷阱 1：Copilot 生成了很多不重要的"建议"，反而增加噪音
  - ✅ 对策：在提示中要求"只列出严重和中等级别的问题，忽略风格偏好"
- ❌ 陷阱 2：Copilot 不了解业务背景，给出了不正确的建议
  - ✅ 对策：在提示中补充关键业务规则，如"这是支付系统，所有金额计算必须使用 Decimal"

---

### 场景 3: 生成标准化的 Review 评论

**问题描述**

你审查代码时，想给出既清晰又专业的评论，但每次都要从头想措辞，效率很低。

**Copilot CLI 解决方案**

```bash
cat << 'EOF' | gh copilot suggest
请根据以下问题生成一条标准化的 Code Review 评论：

问题：代码中使用了 == None 比较，应该用 is None
代码位置：src/utils.py 第 45 行
级别：建议（非阻塞）

评论要求：
- 清楚描述问题
- 解释为什么这样更好（技术原因）
- 提供修改建议（包含修改前后的代码对比）
- 语气友好专业
EOF
```

## 最佳实践速查表

| 任务 | 推荐方式 | 注意事项 |
|------|---------|---------|
| 生成 PR 描述 | `git diff main...HEAD \| copilot suggest` | 拆分大 PR 分别描述 |
| 代码安全扫描 | 说明业务背景 + 要求找安全问题 | 人工验证建议合理性 |
| 生成 Review 评论 | 提供问题位置 + 级别 + 格式要求 | 保持语气专业友好 |
| 检查测试覆盖 | 提供代码 + "是否需要补充测试" | 给出具体的未测场景 |

---

## 常见错误与调试

| 问题 | 症状 | 原因 | 解决方案 |
|------|------|------|---------|
| 生成的建议太笼统 | "这段代码可以优化" | 提示不具体 | 明确要求"指出具体行号和问题类型" |
| 误报业务逻辑问题 | 把正确逻辑标记为 bug | 缺乏业务上下文 | 在提示中补充关键业务规则 |
| PR 描述不完整 | 遗漏了某些文件的说明 | diff 输入被截断 | 分模块生成后人工合并 |

## 进阶延伸

- **自动化 Review 流水线**：在 CI 中配置 Copilot 自动对每个 PR 生成初步审查报告（配合 M8）
- **Review 清单模板**：用 Copilot 为团队生成特定场景的 Review 清单（如"支付功能 Review 清单"）
- **审查风格一致性**：让 Copilot 学习你团队的 Review 风格，生成与团队规范一致的评论
