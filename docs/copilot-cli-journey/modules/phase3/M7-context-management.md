# M7: 上下文管理与多文件交互

## 概览

Copilot CLI 的能力上限很大程度上取决于你给它多少**有效上下文**。在真实项目中，代码分散在多个文件中，如果只提供单个函数，Copilot 往往给不出最好的建议。本模块专注于**如何高效地组织和提供跨文件上下文**，让 Copilot 理解项目结构，从而生成更准确、更符合项目风格的代码建议。

---

## 核心概念 (理论 ~ 30-40%)

### 概念 1: Copilot CLI 的上下文窗口

Copilot CLI 接受文本输入，通过管道 `|` 或重定向 `<` 传入。理解以下特性有助于合理规划上下文：

| 特性 | 说明 | 实际影响 |
|------|------|---------|
| **上下文长度限制** | 每次请求有 token 限制 | 超大文件需要截取关键部分 |
| **顺序优先** | 较早出现的内容权重更高 | 把最重要的信息放在提示开头 |
| **无记忆** | 每次请求独立，不记住上一次 | 需要重复提供必要的上下文 |
| **文件内容 > 描述** | 直接提供代码比描述代码更有效 | 优先用 `cat file.py` 而非描述 |

### 概念 2: 上下文组织策略

根据任务类型选择合适的上下文组织方式：

| 任务 | 推荐上下文策略 | 示例命令 |
|------|--------------|---------|
| 生成单文件测试 | 提供目标文件 | `cat src/utils.py \| copilot suggest` |
| 跨模块分析 | 提供相关文件的关键部分 | 合并多个文件的关键代码 |
| 了解项目结构 | 提供目录树 + README | `tree src/ \| copilot explain` |
| 与现有代码风格一致 | 提供"示例文件" | 先提供风格参考，再提要求 |

### 概念 3: 有效上下文的三层模型

```
第 1 层（必须）：目标代码
  → 你要分析或修改的具体函数/文件

第 2 层（重要）：依赖代码
  → 目标代码调用的函数/类/接口定义

第 3 层（辅助）：项目规范
  → 命名约定、目录结构、测试风格
```

实践原则：**从最小上下文开始，若结果不理想，再逐层增加**。

## 实战应用 (70% 以上)

### 场景 1: 多文件上下文合并分析

**问题描述**

你有一个复杂的 bug：`UserService` 调用 `AuthValidator`，而 `AuthValidator` 依赖 `TokenStore`。bug 可能出在任何一个环节，需要让 Copilot 同时看到这三个文件来帮你定位。

**Copilot CLI 解决方案**

```bash
# 方式 1：用 cat 合并多个文件
(
  echo "=== src/services/user_service.py ==="
  cat src/services/user_service.py
  echo ""
  echo "=== src/auth/validator.py ==="
  cat src/auth/validator.py
  echo ""
  echo "=== src/auth/token_store.py ==="
  cat src/auth/token_store.py
) | gh copilot suggest "以上是三个相互依赖的 Python 文件。
问题现象：用户登录后 15 分钟内 token 会随机失效，但日志没有报错。
请分析可能的 bug 原因，特别关注 token 的生命周期管理。
列出最可能的 3 个原因，并给出对应的修复建议。"
```

**结果与验证**

Copilot 会分析文件间的调用关系，给出基于实际代码的具体建议（而非泛泛的"检查 token 过期"）。

**常见陷阱与对策**

- ❌ 陷阱 1：合并的文件太大，Copilot 只分析了第一个文件
  - ✅ 对策：只提供每个文件的关键函数，而不是整个文件。使用 `grep -A 20 "def target_function"` 提取关键部分
- ❌ 陷阱 2：文件之间的分隔不清晰，Copilot 混淆了来源
  - ✅ 对策：在每个文件前加 `=== 文件名 ===` 标注，如示例所示

### 场景 2: 学习项目代码风格并保持一致

**问题描述**

你加入一个新项目，需要为已有的代码库添加新功能。你希望生成的代码风格与现有代码保持一致，包括命名规范、注释风格、错误处理方式等。

**Copilot CLI 解决方案**

```bash
# Step 1：找一个有代表性的现有功能文件作为"风格模板"
cat src/features/existing_feature.py | gh copilot suggest "请分析以上 Python 文件的代码风格，
并总结：
1. 命名规范（变量、函数、类的命名方式）
2. 错误处理模式（try/except 结构）
3. 注释和 Docstring 风格
4. 函数长度和结构偏好

以 bullet list 格式输出，简洁明了。"

# Step 2：生成新功能时，先提供风格参考
(
  echo "=== 风格参考文件 ==="
  cat src/features/existing_feature.py
  echo ""
  echo "=== 新功能需求 ==="
  echo "请按照以上文件的代码风格，生成一个 ProductService 类，
  包含：create_product(), update_product(), delete_product() 方法。
  接口格式与 existing_feature.py 中的类保持一致。"
) | gh copilot suggest
```

**常见陷阱与对策**

- ❌ 陷阱 1：生成的代码风格仍然偏离项目规范
  - ✅ 对策：在步骤 1 中总结风格后，把总结的规则明确写入步骤 2 的提示中

### 场景 3: 利用目录结构理解项目

**问题描述**

你需要在一个陌生的大型项目中快速定位某个功能，或者理解项目结构后再生成代码。

**Copilot CLI 解决方案**

```bash
# 提供目录结构 + README 关键部分
(
  echo "=== 项目目录结构 ==="
  tree src/ -L 3
  echo ""
  echo "=== README 关键摘要 ==="
  head -50 README.md
) | gh copilot suggest "根据以上项目结构和说明：
1. 支付功能的代码在哪个目录？
2. 如果要添加一个新的支付方式，应该修改哪些文件？
3. 测试文件应该放在哪个位置？"
```

## 最佳实践速查表

| 任务 | 上下文策略 | 关键技巧 |
|------|----------|---------|
| 单文件分析 | 直接 `cat file \| copilot` | 优先用 `<` 重定向 |
| 多文件关联分析 | `echo "=== 文件名 ===" && cat file` | 加分隔标注避免混淆 |
| 保持代码风格 | 先提供"风格参考"文件 | 让 Copilot 先总结风格再生成 |
| 了解项目结构 | `tree src/` + `head README.md` | 控制在 200 行以内 |
| 提取关键部分 | `grep -A N "def function_name"` | 只提供相关函数片段 |

## 常见错误与调试

| 问题 | 症状 | 原因 | 解决方案 |
|------|------|------|---------|
| 建议与项目风格不符 | 生成的代码命名方式不对 | 没有提供风格参考 | 先提供现有代码作为风格示例 |
| 分析结果不准确 | Copilot 误解了代码逻辑 | 上下文不足 | 增加依赖文件作为上下文 |
| 上下文太长被截断 | 只分析了提示的前半部分 | 超出 token 限制 | 提取关键代码片段而非整个文件 |
| 无状态导致重复 | 每次需要重复说明背景 | CLI 无记忆 | 创建"上下文模板文件"复用 |

## 进阶延伸

- **上下文模板文件**：把常用的项目背景信息写成一个 `context.md`，每次使用时一起传入
- **关键代码提取脚本**：写一个 shell 脚本自动提取项目中关键的接口定义和类型声明
- **渐进式上下文**：先问简单问题，再逐步添加上下文，找到"最小有效上下文"
