# M7: 上下文管理与多文件交互

## 学习目标

掌握 GitHub Copilot CLI 在多文件任务中的上下文管理方法，让 Copilot 先理解项目、再收敛范围、最后执行或审查。完成本模块后，你应该能够把复杂请求拆成可验证的上下文步骤，避免 Copilot 在信息不足或范围过大的情况下直接改代码。

## 概览

M7 是 Phase 3 的起点。进入高级阶段后，学习重点不再是让 Copilot 直接生成单个函数、测试或文档，而是训练它如何在真实项目中建立正确上下文。

多文件任务的风险通常不在“不会写代码”，而在“理解错边界”：误改无关文件、忽略调用链、覆盖既有约定、在长会话中丢失关键限制。M7 推荐采用以下工作流：

1. **上下文地图**：先让 Copilot 识别关键文件、职责、依赖关系和可能修改点。
2. **范围收敛**：明确必须修改、可能修改和不应修改的文件或行为。
3. **多文件计划**：把任务拆成 3-5 个可验证步骤，再决定是否执行。
4. **diff 审查**：用最小必要上下文审查改动是否符合目标。
5. **长会话压缩**：使用 `/context`、`/compact` 和阶段性摘要维护会话质量。

## 核心概念

### 1. 上下文不是越多越好

上下文的目标是帮助 Copilot 做出正确判断，而不是把所有文件都塞进会话。高质量上下文通常包含四类信息：

| 类型 | 作用 | 示例 |
| --- | --- | --- |
| 目标上下文 | 说明要达成什么结果 | “实现 M7 主学习模块文档，替换占位内容。” |
| 范围上下文 | 限定哪些文件、模块、命令相关 | “只修改 `M7-context-management.md`。” |
| 证据上下文 | 提供现有结构、相邻模块、验证命令 | “参考 M6、M8 的文档风格；运行 placeholder grep。” |
| 禁止项上下文 | 明确不能做什么 | “不要保留占位词，不要修改其他文件。” |

如果上下文只包含目标，Copilot 可能过度发挥；如果只包含文件内容，Copilot 可能不知道成功标准；如果缺少禁止项，多文件任务就容易产生无关变更。

### 2. 多文件任务先建上下文地图

上下文地图不是实现方案，而是项目理解结果。它应该回答四个问题：

1. **关键文件是什么**：入口文件、配置文件、测试文件、文档文件分别在哪里。
2. **职责是什么**：每个文件或目录承担什么角色。
3. **关系是什么**：调用关系、数据流、依赖关系、文档引用关系如何连接。
4. **可能修改点是什么**：哪些位置最可能需要修改，哪些位置只需要阅读。

先建立地图，再收敛范围，可以显著减少“看起来相关但实际不该改”的误操作。

### 3. 长会话需要主动维护

长会话中，Copilot 可能逐渐遗忘早期约束，或者上下文窗口被无关输出占满。你需要主动维护会话：

- 使用 `/context` 检查当前上下文中有哪些文件、diff 和摘要。
- 使用 `/compact` 压缩长会话，把历史压成更短的可用摘要。
- 在每个阶段结束时写阶段性摘要，记录目标、已完成事项、验证结果和剩余风险。

## 实战应用

### 1. 建立上下文地图

适用场景：你准备让 Copilot 修改多个文件，但还不确定哪些文件真正相关。

可复制 Prompt：

```text
请先不要修改代码。请为这个任务建立上下文地图：

目标：<描述要完成的任务>
范围：<限定目录或文件>
请回答：
1. 关键文件有哪些？每个文件的职责是什么？
2. 文件之间的调用、依赖或引用关系是什么？
3. 哪些文件可能需要修改？哪些文件只需要阅读？
4. 你还缺少哪些证据才能制定修改计划？

输出要求：只输出上下文地图和需要验证的问题，不要执行改动。
```

验证标准：

- 地图能区分“需要阅读”和“需要修改”。
- 每个可能修改点都有证据来源，例如文件路径、函数名、测试名或文档章节。
- 没有把无关目录纳入修改范围。
- Copilot 明确说明不确定信息，而不是直接假设。

### 2. 收敛修改范围

适用场景：上下文地图已经建立，但任务仍可能触碰过多文件。

可复制 Prompt：

```text
基于当前上下文，请先收敛修改范围，不要改文件。

请按三类列出：

必须修改：
- <文件或行为>：<为什么必须改>

可能修改：
- <文件或行为>：<触发条件是什么>

不应修改：
- <文件或行为>：<为什么不应改>

同时列出验证命令，并说明每个命令验证什么。
```

使用建议：

- “必须修改”应该很短，通常是 1-3 个核心文件。
- “可能修改”必须带触发条件，避免变成开放范围。
- “不应修改”要写清楚边界，例如“不改 public API”“不改数据库 schema”“不改无关文档”。

### 3. 多文件任务拆解

适用场景：任务需要跨文件修改，例如功能实现、测试补齐、文档同步、配置调整。

可复制 Prompt：

```text
请把这个多文件任务拆成 3-5 步计划，先不要执行。

任务目标：<目标>
已确认范围：<必须修改 / 可能修改 / 不应修改>

计划格式：
1. <步骤名>
   - 修改文件：<路径>
   - 操作：<具体做什么>
   - 验证：<如何证明这一步正确>
   - 回滚风险：<如果失败，影响是什么>

要求：
- 每一步都必须能独立验证。
- 不要包含超出范围的重构。
- 如果某一步依赖前一步，请明确依赖关系。
```

推荐的 3-5 步结构：

1. 阅读相邻实现或文档，确认风格和约定。
2. 修改最小核心文件。
3. 补齐或更新直接相关测试、示例或文档。
4. 运行针对性验证命令。
5. 审查 diff，确认没有无关变更。

### 4. 使用 diff 做最小上下文审查

适用场景：已经完成修改，需要检查是否符合目标和范围。

常用命令：

```text
/diff
/review
```

可复制 Prompt：

```text
请基于当前 /diff 做最小上下文审查。

审查目标：<任务目标>
范围限制：<只允许修改哪些文件或行为>
验证标准：<必须通过的命令或检查>

请重点检查：
1. diff 是否只包含完成目标所需的最小改动。
2. 是否违反范围限制或引入无关变更。
3. 是否存在遗漏的测试、文档或验证。
4. 是否有命名、边界条件、错误处理或兼容性问题。

输出格式：
- 必须修复
- 建议修复
- 可以接受
```

使用原则：

- 审查时优先提供 diff，而不是重新提供整个项目。
- 如果审查发现范围外改动，先回滚范围外部分，再继续。
- `/review` 适合发现逻辑风险，但最终仍要结合项目验证命令。

### 5. 长会话上下文压缩

适用场景：会话很长、命令输出很多、经历多轮调试或任务跨多个阶段。

常用命令：

```text
/context
/compact
```

阶段性摘要 Prompt：

```text
请生成一个可用于压缩上下文的阶段性摘要，保留后续继续任务所需信息。

请包含：
1. 当前目标和成功标准。
2. 已阅读的关键文件及结论。
3. 已完成的修改和原因。
4. 已运行的验证命令及结果。
5. 仍需完成的步骤。
6. 明确禁止修改或需要保护的范围。

要求：摘要要短，但必须能让后续会话继续工作而不重新探索。
```

推荐流程：

1. 运行 `/context` 查看当前上下文是否过载或包含无关内容。
2. 让 Copilot 生成阶段性摘要。
3. 检查摘要是否保留目标、范围、证据、禁止项。
4. 运行 `/compact` 压缩会话。
5. 压缩后先复述当前任务状态，再继续执行。

## 最佳实践速查表

| 场景 | 推荐做法 | 避免做法 |
| --- | --- | --- |
| 不熟悉项目 | 先建上下文地图 | 直接要求“实现功能” |
| 多文件修改 | 先列必须、可能、不应修改 | 一次性让 Copilot 扫全仓库并改动 |
| 任务范围变大 | 拆成 3-5 步并逐步验证 | 在同一轮里追加多个目标 |
| 审查改动 | 使用 `/diff` 和范围限制 | 只问“看起来对吗” |
| 长会话 | 阶段性摘要后 `/compact` | 依赖模型记住早期约束 |
| 命令输出很长 | 摘要关键错误和验证结果 | 把完整日志反复贴回会话 |
| 有禁止项 | 明确写入 Prompt | 只在心里假设 Copilot 会知道 |

## 常见错误与调试表

| 常见错误 | 表现 | 调试方法 |
| --- | --- | --- |
| 上下文过多 | Copilot 抓不住重点，建议修改无关文件 | 删除无关文件上下文，只保留目标、范围、证据、禁止项 |
| 上下文过少 | Copilot 生成通用方案，不符合项目约定 | 先要求建立上下文地图，引用相邻文件作为证据 |
| 范围没有收敛 | diff 中出现无关重构或格式化 | 重新列“必须修改 / 可能修改 / 不应修改”，回滚范围外改动 |
| 长会话遗忘限制 | 后续步骤违反早期约束 | 用阶段性摘要重申禁止项，再运行 `/compact` |
| 计划不可验证 | 每一步都很抽象，无法判断完成 | 要求每步包含文件路径、操作和验证命令 |
| 审查只看最终结果 | 忽略隐藏副作用或兼容性问题 | 基于 `/diff` 审查最小改动，并运行项目已有验证 |
| Prompt 同时要求探索和执行 | Copilot 在未确认上下文时直接改文件 | 在 Prompt 中明确“先不要修改代码” |

## 推荐练习

1. **文档任务练习**：选择一个占位模块文档，让 Copilot 先建立上下文地图，再只修改目标文档。
2. **测试补齐练习**：选择一个已有函数，让 Copilot 找到实现文件、测试文件和相邻测试风格，再提出 3 步测试计划。
3. **配置变更练习**：选择一个 lint、build 或 CI 配置项，要求 Copilot 列出必须修改、可能修改和不应修改的文件。
4. **diff 审查练习**：完成一个小改动后，使用 `/diff` 和 `/review` 检查是否存在范围外变更。
5. **长会话压缩练习**：模拟一个包含探索、修改、验证的长任务，在中途生成阶段性摘要并运行 `/compact`。

## 与其他模块的关系

- **M6：高级集成**：M6 关注如何把 Copilot 放进更复杂的开发流程；M7 为这些流程提供上下文管理基础，确保集成任务不会失控。
- **M5：文档生成**：M5 训练如何生成高质量文档；M7 进一步要求文档任务先理解相邻结构、读者对象和修改边界。
- **M8：自定义工作流与脚本集成**：M8 会把常用流程脚本化；M7 的上下文地图、范围收敛和 diff 审查可以沉淀为可复用工作流。

## 反思与迭代

完成一次多文件任务后，建议用以下问题复盘：

1. 我是否在执行前建立了足够清晰的上下文地图？
2. 哪些信息后来证明是关键证据？这些信息能否更早提供？
3. diff 中是否出现过范围外改动？原因是目标、范围、证据还是禁止项缺失？
4. 验证命令是否覆盖了真正的风险？是否只验证了表面格式？
5. 如果会话继续变长，我的阶段性摘要能否让另一个会话无缝接手？

迭代的关键不是写更长的 Prompt，而是让 Prompt 更结构化、更可验证、更能约束范围。
