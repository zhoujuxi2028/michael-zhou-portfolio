# M9: 调试与故障排查

## 概览

使用 Copilot CLI 一段时间后，你会遇到这样的情况：生成的建议质量参差不齐——有时一针见血，有时完全偏题。本模块专注于**识别低质量建议的规律**、**分析 Copilot 给出错误答案的原因**，以及通过**迭代优化提示**来持续改进建议质量。掌握这些技巧，能让你更高效地与 Copilot 协作。

---

## 核心概念 (理论 ~ 30-40%)

### 概念 1: 低质量建议的常见类型

| 类型 | 表现特征 | 根本原因 |
|------|---------|---------|
| **过于泛化** | "你可以尝试更好的命名..." | 上下文太少，Copilot 不了解具体情况 |
| **逻辑错误** | 生成的代码有 bug 或逻辑不通 | 提示中对预期行为描述不清楚 |
| **框架不符** | 用了错误的库或 API | 没有指定框架版本或项目约束 |
| **重复内容** | 生成了已有的代码 | 没有告诉 Copilot 已有的实现 |
| **过度复杂** | 生成了过于复杂的解决方案 | 没有约束复杂度要求 |

### 概念 2: 提示诊断流程

当 Copilot 给出不满意的结果时，按以下顺序排查：

```
Step 1：上下文是否足够？
  → 是否提供了相关代码文件？
  → 是否说明了项目背景？

Step 2：任务是否清晰？
  → 任务描述是否有歧义？
  → 是否混合了多个不相关的要求？

Step 3：约束是否明确？
  → 是否指定了框架/版本？
  → 是否说明了不能做什么？

Step 4：示例是否有帮助？
  → 提供一个期望输出的例子
  → 提供一个"不好"的示例让 Copilot 避免
```

### 概念 3: 错误分析模式

使用 Copilot CLI 本身来分析错误，形成**"用 AI 调试 AI"**的反馈循环：

```bash
# 当 Copilot 给出了错误的建议时，直接问它为什么
echo "上一次你建议我这样实现：
<错误的建议代码>

但这个实现有以下问题：
1. 在边界条件 X 下会崩溃
2. 忽略了 Y 情况

请解释为什么你的建议有这些问题，并给出改进版本。" | gh copilot suggest
```

## 实战应用 (70% 以上)

### 场景 1: 分析复杂错误信息

**问题描述**

测试失败，但错误信息很长且涉及多层异常，手动追踪需要 20 分钟。希望 Copilot 帮你快速定位根本原因。

**Copilot CLI 解决方案**

```bash
# 直接把错误日志传给 Copilot
pytest tests/integration/ --tb=long 2>&1 | gh copilot suggest \
"以上是 pytest 的错误日志。请：
1. 找出最根本的错误原因（不是 Traceback 的最后一行，而是真正的根因）
2. 排除'因为上面的错误导致的'次生错误
3. 给出 2-3 个可能的修复方向，按可能性从高到低排序
用中文简洁回答。"
```

**实际效果示例**

输入：500 行 Traceback，包含多层嵌套异常

输出：
```
根本原因：数据库连接池耗尽（ConnectionPool exhausted）
位置：src/db/pool.py 第 134 行，_acquire() 方法等待超时

次生错误（由此引起，可忽略）：
- UserService 的 7 个测试失败 — 都是因为数据库不可用
- AuthValidator 的 3 个测试失败 — 同上

修复方向（按可能性排序）：
1. 检查 pool_size 配置，当前为 5，可能对测试环境太小
2. 确认测试 teardown 是否正确关闭了连接（连接泄漏）
3. 增加 pool_timeout 配置，但这只是缓解不是根治
```

**常见陷阱与对策**

- ❌ 陷阱 1：Copilot 只描述了 Traceback 中的最后一条错误，没有找到根因
  - ✅ 对策：在提示中明确"找出根本原因，不是最后一行 Exception"

### 场景 2: 迭代优化低质量提示

**问题描述**

你写了一个提示让 Copilot 生成代码，但结果不理想。需要系统地改进提示，而不是反复猜测。

**诊断和优化流程**

```bash
# 第一次提示（结果不满意）
cat << 'EOF' | gh copilot suggest
生成一个用户注册函数
EOF
# 结果：太简单，没有验证，没有错误处理

# 第二次：加入缺失的约束
cat << 'EOF' | gh copilot suggest
使用 Python 生成一个 register_user() 函数，要求：
1. 参数：username(str), email(str), password(str)
2. 验证：email 格式、密码长度 >= 8
3. 错误处理：ValidationError 包含字段名和错误描述
4. 返回：成功时 {"user_id": ..., "created_at": ...}
5. 不使用外部库，只用 Python 标准库

一个参数验证失败的示例：
输入: register_user("john", "not-email", "123")
预期: 抛出 ValidationError({"email": "格式无效", "password": "长度不足"})
EOF
```

**提示迭代对比表**

| 提示版本 | 关键改进 | 结果质量变化 |
|----------|---------|------------|
| v1：一句话 | — | ⭐ 太简单 |
| v2：加入参数说明 | 明确参数类型 | ⭐⭐ 有改善 |
| v3：加入约束和示例 | 添加约束 + 示例输入/输出 | ⭐⭐⭐⭐ 接近预期 |

**常见陷阱与对策**

- ❌ 陷阱 1：每次修改提示后期望立刻得到完美结果
  - ✅ 对策：把提示优化当成迭代过程，每次只改一个变量，观察效果变化

### 场景 3: 处理 Copilot 的"幻觉"输出

**问题描述**

Copilot 有时会自信地生成"不存在的 API"或"错误的参数格式"。你需要学会识别和纠正这类问题。

**识别幻觉的方法**

```bash
# 方式 1：让 Copilot 自我验证
cat << 'EOF' | gh copilot suggest
你刚刚建议我使用 requests.get(url, verify_ssl=True)，
请确认：Python requests 库的 get() 方法是否真的有 verify_ssl 参数？
如果没有，正确的参数名是什么？
EOF

# 方式 2：要求提供来源
cat << 'EOF' | gh copilot suggest
你建议的 PyYAML 4.0 API 是否真实存在？
请列出 PyYAML 中读取 YAML 文件的正确方式，
包含实际可运行的代码示例。
EOF
```

**判断建议可信度的经验规则**

- ✅ **高可信**：通用编程模式（循环、异常处理）、主流库的核心 API
- ⚠️ **中可信**：第三方库的高级功能、特定版本的 API
- ❌ **低可信**：具体版本号、复杂配置参数、不常用的边缘功能

## 最佳实践速查表

| 问题 | 调试方向 | 改进策略 |
|------|---------|---------|
| 建议太泛化 | 上下文不足 | 提供代码文件和项目背景 |
| 建议有 bug | 任务描述不清 | 添加输入/输出示例 |
| 框架不对 | 约束不明确 | 指定框架名称和版本 |
| 出现幻觉 API | 需要验证 | 让 Copilot 自我验证，查官方文档 |
| 结果不一致 | 提示有歧义 | 简化提示，一次只问一件事 |

---

## 常见错误与调试

| 问题 | 症状 | 原因 | 解决方案 |
|------|------|------|---------|
| 每次结果差异很大 | 相同提示给出不同答案 | Copilot 的随机性 | 添加格式约束减少变化空间 |
| 无法找到真正根因 | 只描述表面错误 | 错误日志太长被截断 | 只传最后 50 行并加 `--tb=short` |
| 建议与现有代码冲突 | 生成的代码重复已有实现 | 没有提供现有代码 | 先 cat 现有代码，再提需求 |

## 进阶延伸

- **建立个人"失败案例库"**：记录 Copilot 给出错误建议的场景，总结规律，改进提示习惯
- **A/B 测试提示**：同一个问题用两种不同的提示方式，比较结果差异，找到最有效的表达方式
- **建立验证清单**：对于关键代码，让 Copilot 生成后，再用 Copilot 审查一遍，形成双重检验
