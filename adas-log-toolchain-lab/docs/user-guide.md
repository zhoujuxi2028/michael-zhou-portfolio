# User Guide

[中文](user-guide.zh.md) | English

`adas-lab` is a command-line toolchain for ADAS (ACC / APA / HMI / LKA) event logs: it generates logs, detects anomalies, turns them into regression cases, replays them, records trigger-based clips, maps tickets to check scripts, and feeds a dashboard.

> **Simulation lab, synthetic data only.** Every log, ticket and number in this project is generated by the tool itself. It is not connected to any vehicle, bench or production system. See [Limitations](#12-limitations-and-gap-to-production).

All commands below were run against this repository (`adas-log-toolchain-lab/`); output excerpts are real.

## 1. Install and requirements

| Component | Requirement |
|-----------|-------------|
| CLI (`src/`) | Node.js >= 22.18 (runs `.ts` files natively, no build step) |
| Analysis (`analysis/`) | Python 3.13 + pandas (`analysis/requirements.txt`) |
| Dashboard (`dashboard/`) | Node.js >= 22.18, Vite + ECharts (own `package.json`) |

```bash
cd adas-log-toolchain-lab
npm ci
node src/cli.ts --version     # 0.2.0
npm run adas -- --help        # same as: node src/cli.ts --help
```

Optional parts:

```bash
# analysis
cd analysis && python3.13 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
# dashboard
cd dashboard && npm ci
```

`out/` is the default output directory and is git-ignored.

## 2. Quick start

```bash
npm run demo     # gen -> parse -> cases boundary
```

Or step by step:

```bash

node src/cli.ts parse out/events.jsonl                # out/anomalies.json
node src/cli.ts cases boundary                        # out/cases/boundary/
node src/cli.ts cases regression --anomalies out/anomalies.json --log out/events.jsonl
```

## 3. Commands

```text
adas-lab [options] [command]
  gen                 Generate synthetic ADAS logs and truth labels
  parse <input>       Detect anomalies in a JSON Lines log
  cases boundary      Generate boundary value cases from rule thresholds and verify them
  cases regression    Turn detected anomalies into self-contained regression cases
  replay              Replay regression cases from a manifest and report pass / fail
  record              Record trigger-based clips from a log file or the live generator stream
  ticket <export>     Turn a synthetic Jira export into script tasks and check scripts
```

Global: `-V, --version`, `-h, --help` (also per command). Exit codes: `0` ok, `1` a gate triggered (see each command), `2` usage / input error (message on stderr, prefixed `error:`).

### 3.1 `gen`

Generate a reproducible synthetic log plus truth labels (the faults injected).

| Option | Default | Notes |
|--------|---------|-------|
| `--seed <n>` | 42 | integer; same seed gives byte-identical output |
| `--scenarios <n>` | 20 | integer >= 8 |
| `--interleave` | off | sort all events by `ts` across scenarios (simulates a multiplexed bus) |
| `--out <dir>` | `out` | writes `events.jsonl`, `labels.json` |

Scenarios cycle through ACC, APA and LKA (the first 8 alternate ACC / APA); the first scenarios carry injected faults, one per rule behavior.

```bash
node src/cli.ts gen --seed 7 --scenarios 12 --interleave --out out/s7
```

Exit: `0`; `2` for non-integer `--seed` / `--scenarios`, or `--scenarios < 8`.

### 3.2 `parse`

Stream a JSON Lines log through the rule engine and write `anomalies.json`.

| Option | Default | Notes |
|--------|---------|-------|
| `<input>` | required | `.jsonl` file |
| `--out <file>` | `out/anomalies.json` | |
| `--config <file>` | none | rule config JSON, see [section 6](#6-rule-config-override) |
| `--fail-on <P1\|P2>` | none | exit 1 if any anomaly of that severity or above (`P1`: any P1; `P2`: any anomaly) |
| `--strict` | off | exit 1 on any data quality issue |

```bash
node src/cli.ts parse out/events.jsonl --fail-on P1
```

```text
Parsed 16879 events in 20 scenarios
Anomalies: 16 (P1: 10, P2: 6)
Data quality: invalid JSON 0, schema errors 0, unknown events 0, out of order 0
Report written to out/anomalies.json
```

(exit code 1 here because the synthetic log contains P1 faults). Exit `2`: input not found, bad config.

### 3.3 `cases boundary`

For every rule, build boundary-value cases (threshold -epsilon / exact / +epsilon), write them, and verify each through the parser: exactly the target rule may fire, and only on the expected side.

| Option | Default |
|--------|---------|
| `--out <dir>` | `out/cases` (writes `boundary/`) |
| `--config <file>` | none (thresholds and `epsilon` come from the config) |

```text
38 boundary cases written to out/cases/boundary; 38 passed, 0 failed
```

Exit: `0` all passed; `1` any case failed (a `FAIL <caseId>: ...` line per failure on stderr); `2` bad config.

### 3.4 `cases regression`

Turn every anomaly in `anomalies.json` into a self-contained regression case (events in a window around the anomaly plus the preconditions needed to reproduce it), a `manifest.json`, and a generated Vitest file.

| Option | Default | Notes |
|--------|---------|-------|
| `--anomalies <file>` | required | from `parse` |
| `--log <file>` | required | the original log |
| `--out <dir>` | `out/cases` | |
| `--pre <ms>` | 3000 | window start = `startTs - pre` (>= 0) |
| `--post <ms>` | 3000 | window end = `detectTs + post` (>= 0) |

```text
16 regression cases written to out/cases/manifest.json; test file out/cases/generated/regression.test.ts
```

Case data goes through the same scanner as `parse`: invalid and late events are dropped and window events are sorted by `ts`. Every case file must stay under `--out`. Before writing, the command removes the previous `data/`, `generated/` and `manifest.json` under `--out`; other files are kept, so do not point `--out` at a directory that holds your own `generated/` folder.

Exit: `0`; `2` anomalies / log file missing or invalid (including an invalid `scenarioId` in the anomalies file), or a case path outside `--out`. Run the generated tests with `npm run test:generated` (see [3.8](#38-generated-tests)).

### 3.5 `replay`

Replay every manifest case through the rule engine (using its window) and report PASS / FAIL. A case passes only when the target rule fires as expected and the case data has no data quality issues.

| Option | Default | Notes |
|--------|---------|-------|
| `--manifest <file>` | required | `manifest.json` from `cases regression` |
| `--out <file>` | `out/replay-report.json` | |
| `--filter <expr>` | none | `module=<ACC\|APA\|HMI\|LKA>` |

```bash
node src/cli.ts replay --manifest out/cases/manifest.json --filter module=APA
```

```text
Replayed 4 cases: 4 passed, 0 failed (pass rate 100.0%) -> out/r-apa.json
```

Exit: `0` all passed; `1` any FAIL (one line per case on stderr: `FAIL <caseId>: expected <rule> to fire; fired rules [...]`, `expected <rule> not to fire`, `case data has N data quality issues`, or `error <message>`); `2` manifest missing / malformed, invalid `--filter`. A manifest is malformed if `expect.ruleId` differs from `ruleId`, `window[0] > window[1]`, or `source` resolves outside the manifest directory. Other rules firing in a case (for example `HMI-01` caused by window truncation) is recorded in `firedRules` and is not a failure.

### 3.6 `record`

Simulated data logger: per-scenario ring buffer, trigger-based clip recording (rule hit or `SYS/MANUAL_TRIGGER`), clip splitting, an index with SHA-256, and capture quality checks.

| Option | Default | Notes |
|--------|---------|-------|
| `--source <file\|live>` | `file` | |
| `--input <jsonl>` | none | required for `--source file`; invalid with `live` |
| `--seed <n>` | 42 | `live` only (integer) |
| `--scenarios <n>` | 20 | `live` only (>= 8) |
| `--speed <n>` | 1 | `live` playback factor (> 0; virtual clock, `100000` finishes in about 1 s) |
| `--out <dir>` | `out/clips` | |
| `--buffer <ms>` | 10000 | ring buffer length per scenario (positive integer) |
| `--pre <ms>` | 5000 | recorded before the anomaly `startTs` (integer >= 0) |
| `--post <ms>` | 5000 | recorded after `detectTs` (integer >= 0) |

Behavior: a clip covers `[startTs - pre, detectTs + post]` (or until scenario end); if the start is older than the buffer the clip is cut and flagged `truncated: true`; overlapping windows in one scenario are merged only while the first clip is still recording (file name uses the first trigger). A merged clip is capped at `maxClipMs` (default 60000 + pre + post, 70 s with the defaults); a longer merge starts a new clip. A lone event that jumps more than 1000 ms ahead and that the next event does not continue from is treated as a spike: it is not recorded, but quality still counts it. Clip file names are sanitized and always inside `--out`. Every clip starts with the preconditions (latest `ACC/STATE`, `APA/STEP`, `LKA/STATE`, `VEH/TURN_SIGNAL` before the window) so it can be replayed alone.

```bash
node src/cli.ts record --source file --input out/events.jsonl --out out/clips
node src/cli.ts record --source live --seed 42 --speed 100000 --out out/clips-live
```

```text
Recorded 16879 events in 20 scenarios from out/events.jsonl
Clips: 16 (rule 16, manual 0, truncated 2)
Quality: TRACK frames 9600, dropped 0 (0%), duplicates 0, ts anomalies 15
Skipped lines: invalid JSON 0, schema errors 0, unknown events 0, out of order 0
Clips written to out/clips
```

Outputs: `<scenarioId>_<startTs>_<ruleId|MANUAL>.jsonl` clips, `index.json`, `quality.json` ([section 7](#7-outputs-reference)). Exit: `0` (recording has no pass / fail gate); `2` missing `--input` with `--source file`, input not found, `--input` with `--source live`, bad `--source`, non-positive `--speed` / `--buffer`, negative `--pre` / `--post`, `--scenarios < 8`. `record` does not accept `--config`: it always uses default rule thresholds.

### 3.7 `ticket`

Map a synthetic Jira REST v2 style export to script tasks and generated check scripts.

| Option | Default | Notes |
|--------|---------|-------|
| `<export>` | required | JSON `{ "issues": [ { "key", "fields": { "summary", "description", "components": [{ "name" }], "labels": [] } } ] }` |
| `--out <dir>` | `out/tasks` | |
| `--config <file>` | none | thresholds used for the repro cases |
| `--strict` | off | exit 1 if any ticket is unmapped |

Mapping: the label `rule:<ID>` (case-insensitive) selects the rule; the `components` list must contain the rule's module; the description sections `Steps` / `Expected` (Jira wiki `h3. Steps`, `*Steps*`, or `Steps:`) become `steps[]` / `expected[]`. The repro data is the rule's boundary cases that must trigger.

```bash
node src/cli.ts ticket fixtures/jira/export.json
```

```text
6 tickets: 3 mapped, 3 unmapped; tasks written to out/tasks
See out/tasks/unmapped.json for reasons
```

Before writing, `ticket` removes stale `data/`, `generated/`, `unmapped.json` and its own `<KEY>.json` task files under `--out`.

Unmapped reasons: `no rule label`, `unknown rule id`, `component does not match rule module`. Exit: `0` (also with unmapped tickets); `1` unmapped tickets with `--strict`; `2` export missing / not valid JSON / wrong shape / duplicate issue key.

### 3.8 Generated tests

`cases regression` and `ticket` write Vitest files under a `generated/` directory. Run all of them:

```bash
npm run test:generated      # vitest.generated.config.ts: **/generated/**/*.test.ts
```

```text
 Test Files  4 passed (4)
      Tests  21 passed (21)
```

It passes (exit 0) when no generated tests exist yet (`--passWithNoTests`). Generated tests import `src/casegen/case-runner.ts` by relative path: keep the output inside this directory tree, and do not edit them (regenerate instead).

### 3.9 Analysis and dashboard

```bash
# from analysis/ (Python 3.13 venv with pandas)
python -m adas_analysis --anomalies ../out/anomalies.json [--replay ../out/replay-report.json] --out ../out/summary.json
# from dashboard/
npm run dev        # http://localhost:5173, uses public/summary.json (sample)
npm run build      # tsc --noEmit && vite build -> dist/
```

`adas_analysis` exit codes: `0`; `2` missing / invalid input (message on stderr, e.g. `error: anomalies file not found: ../out/nope.json`). Field types are validated (severity `P1` / `P2`, integer `ts`, `dataQuality` counts, replay summary); the message names the field and index. To view your own data in the dashboard, write the summary to `dashboard/public/summary.json` before `npm run dev` / `build` (the file in the repo is a sample). The GitHub Pages workflow does this automatically on `main`.

## 4. Event format

One JSON object per line (JSON Lines). Envelope:

| Field | Type | Notes |
|-------|------|-------|
| `ts` | integer >= 0 | scenario time, milliseconds |
| `scenarioId` | string | `^[A-Za-z0-9_.-]{1,64}$`, not `.` or `..` (it names output files; anything else is a schema error); events of one scenario share it |
| `module` | string | see table |
| `type` | string | see table |
| `data` | object | payload per `module/type` |

```json
{"ts":50,"scenarioId":"S001","module":"ACC","type":"TRACK","data":{"egoSpeed":17.21,"setSpeed":19.23,"leadDistance":26.83,"leadRelSpeed":0.2}}
```

| module / type | `data` fields |
|---------------|---------------|
| `ACC/STATE` | `from`, `to` in `OFF` `STANDBY` `ACTIVE` `OVERRIDE`; `reason` string |
| `ACC/TRACK` | `egoSpeed` >= 0 (m/s), `setSpeed` >= 0, `leadDistance` >= 0 or `null` (m), `leadRelSpeed` (m/s) |
| `ACC/BRAKE_PEDAL` | `pressed` boolean |
| `ACC/TAKEOVER_REQUEST` | `reason` string |
| `APA/STEP` | `step` in `SEARCHING` `SLOT_SELECTED` `MANEUVERING` `COMPLETED` `ABORTED`; `reason` string |
| `APA/OBSTACLE` | `minDistance` >= 0 (m) |
| `HMI/DISPLAY` | `feature` in `ACC` `APA` `LKA`; `item` in `STATE` `TAKEOVER` `UNAVAILABLE`; `value` string |
| `LKA/STATE` | `from`, `to` in `OFF` `STANDBY` `ACTIVE` `SUPPRESSED` `UNAVAILABLE` |
| `LKA/LANE` | `leftConf`, `rightConf` in [0, 1]; `offset` (m) |
| `LKA/STEER` | `torque` (Nm, signed) |
| `VEH/TURN_SIGNAL` | `side` in `LEFT` `RIGHT` `OFF` |
| `SYS/SCENARIO_END` | `{}`: closes the scenario; pending window rules are judged |
| `SYS/MANUAL_TRIGGER` | `note` string; asks `record` for a clip |

Within a scenario, events should be in `ts` order. Extra keys in `data` are not part of the contract; wrong types are schema errors ([section 9](#9-data-quality-handling)).

## 5. Rules

Ruleset version `1.1.0`. P1 = safety relevant, P2 = functional / indication. Times in ms, distances in m, torque in Nm.

| Id | Sev | Anomaly when | Config keys (defaults) |
|----|-----|--------------|------------------------|
| `ACC-01` | P1 | ACC is `ACTIVE` and `leadDistance < max(minGapM, egoSpeed * timeGapS)`. Hits closer than `mergeGapMs` form one anomaly (`startTs` first hit, `endTs` last hit); closed when ACC leaves `ACTIVE` or the scenario ends | `minGapM` 5, `timeGapS` 1.0, `mergeGapMs` 200 |
| `ACC-02` | P1 | Brake pedal pressed while ACC `ACTIVE`, and ACC is not `STANDBY` / `OFF` within `exitWindowMs` | `exitWindowMs` 200 |
| `APA-01` | P1 | During `MANEUVERING`, `APA/OBSTACLE.minDistance < minDistanceM` and no `ABORTED` step within `abortWindowMs` | `minDistanceM` 0.3, `abortWindowMs` 200 |
| `APA-02` | P2 | `MANEUVERING` lasts longer than `timeoutMs` without `COMPLETED` / `ABORTED`; also reported (as unfinished) at scenario end | `timeoutMs` 60000 |
| `HMI-01` | P2 | After an ACC / APA / LKA state change, the HMI `STATE` display for that feature does not show the new value within `displayWindowMs` (missing, or a different value) | `displayWindowMs` 300 |
| `HMI-02` | P1 | `ACC/TAKEOVER_REQUEST` is not followed by `HMI/DISPLAY` with `item=TAKEOVER` within `takeoverWindowMs` | `takeoverWindowMs` 200 |
| `LKA-01` | P1 | `VEH/TURN_SIGNAL` is `LEFT` / `RIGHT` and `abs(LKA/STEER.torque) > torqueNm`; merged like ACC-01; closed when the signal goes `OFF` | `torqueNm` 0.5, `mergeGapMs` 200 |
| `LKA-02` | P2 | `min(leftConf, rightConf) < confThreshold` persists longer than `persistMs` (strict), and no `HMI/DISPLAY(LKA, UNAVAILABLE)` appears by `loss start + persistMs + displayWindowMs`; recovery before `persistMs` discards the loss | `confThreshold` 0.5, `persistMs` 500, `displayWindowMs` 300 |

Boundary semantics: thresholds are strict, so a value exactly at the threshold does not fire (the `eq` boundary case). Window rules are judged when scenario time passes the deadline, or at scenario end.

Boundary epsilons (used only by `cases boundary` / `ticket`): `distance` 0.01 m, `time` 1 ms, `torque` 0.01 Nm.

### Anomaly record

| Field | Meaning |
|-------|---------|
| `ruleId`, `module`, `severity` | which rule fired |
| `scenarioId` | scenario |
| `startTs` | event that started the judgment (threshold rules: first hit) |
| `endTs` | threshold rules: last hit; window rules: deadline; unfinished flows: `SCENARIO_END` ts |
| `detectTs` | scenario time at which the rule decided |
| `message` | English description |
| `evidence` | rule specific values (e.g. `minDistance`, `threshold`; may be `{}`) |

## 6. Rule config override

`--config <file>` (on `parse`, `cases boundary`, `ticket`) overrides defaults. Only the listed keys change; the rest keep their defaults. Unknown keys, unknown rule ids and extra top-level keys are rejected with exit 2.

```json
{
  "rules": {
    "ACC-01": { "minGapM": 8, "timeGapS": 1.5 },
    "HMI-01": { "displayWindowMs": 500 }
  },
  "epsilon": { "distance": 0.05 }
}
```

```bash
node src/cli.ts parse out/events.jsonl --config rules.config.json --out out/anomalies-strict.json
```

Stricter ACC-01 values flag many more events (with `minGapM: 8, timeGapS: 1.5` the default log yields 106 anomalies instead of 16), which is expected.

```text
error: invalid config: unknown rule id "XX"
error: invalid config: unknown key "foo" for rule ACC-01
```

Values must be numbers. `epsilon` keys: `distance`, `time`, `torque` (positive). Note: changing a default or a config does not change the ruleset version; see the [dev guide](dev-guide.md#8-versioning).

## 7. Outputs reference

All JSON files are written with 2-space indent and a trailing newline. Files that come from the tool carry `meta.toolVersion` and `meta.rulesetVersion`.

### `anomalies.json` (`parse`)

| Field | Content |
|-------|---------|
| `meta` | `input`, `events`, `scenarios`, `toolVersion`, `rulesetVersion` |
| `anomalies[]` | anomaly records ([above](#anomaly-record)) |
| `summary` | `byRule` (count per rule id), `bySeverity` (`P1`, `P2`) |
| `dataQuality` | `counts` (`invalidJson`, `schemaErrors`, `unknownEvents`, `outOfOrder`), plus detail lists |

### `labels.json` (`gen`)

`[ { scenarioId, ruleId, startTs, endTs } ]`: the truth. Tests compare detected anomalies with it (one-to-one match on scenario + rule + overlapping interval).

### Boundary cases (`cases boundary`)

`out/cases/boundary/<caseId>.jsonl` (a complete scenario) and `expected.json`:

```json
{ "caseId": "ACC-01-lowspeed-minus", "ruleId": "ACC-01", "file": "ACC-01-lowspeed-minus.jsonl",
  "expectTriggered": true, "description": "lead distance 4.99 m vs threshold 5.00 m at 3 m/s" }
```

Case ids end in `-minus` / `-eq` / `-plus` (threshold minus epsilon, exact, plus epsilon).

### `manifest.json` (`cases regression`, contract C1)

| Field | Content |
|-------|---------|
| `meta` | versions, `anomalies`, `log`, `preMs`, `postMs` |
| `cases[]` | `caseId` (`REG-<ruleId>-<scenarioId>-<startTs>`, repeats get `-2`, `-3`), `ruleId`, `scenarioId`, `source` (data file, relative to the manifest), `window` `[from, to]`, `expect` `{ ruleId, triggered }` |

`window[0]` can be earlier than `startTs - pre`: it is moved back to the oldest precondition event so replay never cuts it off.

### `replay-report.json` (`replay`, contract C2)

| Field | Content |
|-------|---------|
| `meta` | versions, `manifest`, `filter` (`module=APA` or `null`) |
| `results[]` | `caseId`, `ruleId`, `status` (`PASS` / `FAIL`), `firedRules`, `durationMs`, optional `dataQualityIssues` (count; non-zero fails the case), optional `error` (case could not run) |
| `summary` | `total`, `passed`, `failed`, `passRate` (0..1, 4 decimals; 0 when no cases) |

### `summary.json` (`adas_analysis`, contract C4)

| Field | Content |
|-------|---------|
| `meta` | versions, `analysisVersion`, `anomalies`, `replay` (path or `null`) |
| `totals` | `events`, `scenarios`, `anomalies`, `p1`, `p2` |
| `byRule[]` | `ruleId`, `module`, `severity`, `count` (sorted by rule id) |
| `byModule[]` | `module`, `count` |
| `byScenario[]` | `scenarioId`, `count`, `p1`, `p2` (only scenarios with anomalies) |
| `timeline[]` | `bucketStartMs`, `count`: 5 s buckets by `startTs`, contiguous including empty buckets |
| `dataQuality` | the four counters |
| `replay` | `{ total, passed, failed, passRate }` or `null` without `--replay` |

### `tasks/` (`ticket`, contract C5)

| File | Content |
|------|---------|
| `<KEY>.json` | `key`, `summary`, `module`, `ruleId`, `steps[]`, `expected[]`, `cases[]` (case ids), `testFile` |
| `data/<KEY>-<caseId>.jsonl` | repro scenario |
| `generated/<KEY>.test.ts` | generated check script |
| `unmapped.json` | `[ { key, reason } ]` |

### Clips (`record`, contract C3)

`index.json`:

| Field | Content |
|-------|---------|
| `meta` | versions, `source` (`live` or input path), `bufferMs`, `preMs`, `postMs` |
| `clips[]` | `file`, `scenarioId`, `trigger` (`rule` / `manual`), `ruleIds[]`, `startTs`, `endTs`, `events` (lines in the file, preconditions included), `sha256` (of the file bytes), `truncated` |

`quality.json`:

| Field | Content |
|-------|---------|
| `trackPeriodMs` | 50 |
| `totals`, `byScenario[]` | `trackFrames`, `droppedFrames`, `dropRate`, `duplicates`, `tsAnomalies` (+ `scenarioId`) |

Definitions: a gap between adjacent `ACC/TRACK` frames of one scenario above 75 ms (1.5 periods) counts `round(gap / 50) - 1` dropped frames; a duplicate is a line identical to the previous line of the same scenario; a ts anomaly is a `ts` earlier than the previous event, or a gap above 1000 ms from the previous event, in one scenario (so one isolated spike counts as two anomalies).

## 8. End-to-end workflow

```text
                  gen --seed --scenarios
                          |
              events.jsonl + labels.json            (or: real/other logs)
                          |
          +---------------+----------------+
          |                                |
   parse [--config]                  record --source file|live
          |                                |
   anomalies.json                 clips/*.jsonl, index.json, quality.json
     |         |
     |   cases regression --anomalies --log
     |         |
     |   manifest.json + data/*.jsonl + generated/regression.test.ts
     |         |                       |
     |      replay [--filter]    npm run test:generated
     |         |
     |   replay-report.json
     |         |
     +----> python -m adas_analysis --anomalies [--replay]
                   |
              summary.json --> dashboard (npm run build) --> GitHub Pages

   cases boundary [--config]  -->  boundary/*.jsonl + expected.json  (self-check of the rules)
   ticket export.json         -->  tasks/<KEY>.json + generated/<KEY>.test.ts + unmapped.json
```

Full pipeline into `out/` (every line was run; all exit 0 on the default synthetic data):

```bash
node src/cli.ts gen --out out
node src/cli.ts parse out/events.jsonl --out out/anomalies.json
node src/cli.ts cases boundary --out out/cases
node src/cli.ts cases regression --anomalies out/anomalies.json --log out/events.jsonl --out out/cases
node src/cli.ts replay --manifest out/cases/manifest.json --out out/replay-report.json
node src/cli.ts record --source file --input out/events.jsonl --out out/clips
node src/cli.ts ticket fixtures/jira/export.json --out out/tasks
npm run test:generated
(cd analysis && python -m adas_analysis --anomalies ../out/anomalies.json --replay ../out/replay-report.json --out ../out/summary.json)
(cd dashboard && npm run build)
```

CI use (gating): `parse --fail-on P1 --strict`, `cases boundary` (fails when a rule drifts from its thresholds), `replay` (fails when a recorded anomaly no longer reproduces).

## 9. Data quality handling

`parse` and `record` never stop on bad input. Problems are counted, the line is skipped, and the run continues.

| Counter | Cause | Detail kept |
|---------|-------|-------------|
| `invalidJson` | line is not JSON, or longer than 1 MiB | `line`, `detail` (max 100) |
| `schemaErrors` | JSON but wrong envelope or payload (types, enums, negative `ts`) | `line`, `detail` (max 100) |
| `unknownEvents` | valid envelope with an unknown `module/type` | map key -> count (max 100 distinct keys, then `(other)`) |
| `outOfOrder` | `ts` goes backwards inside a scenario, or an event arrives after its scenario ended with `ts` earlier than the end | `line`, `scenarioId`, `ts`, `prevTs` (max 100) |

Rules: blank lines are ignored; a UTF-8 BOM on line 1 is ignored; late events of an ended scenario are dropped (they cannot reopen it); a reused scenario id after `SCENARIO_END` counts as a new scenario. Out-of-order events inside an open scenario still reach the rules, which only widen episodes, never shrink them.

Sample with `fixtures/bad-lines.jsonl` (exit 0; `--strict` makes it exit 1):

```text
Parsed 4 events in 1 scenarios
Anomalies: 1 (P1: 0, P2: 1)
Data quality: invalid JSON 1, schema errors 2, unknown events 1, out of order 1
Report written to out/bad.json
```

## 10. Exit codes

| Code | Meaning | Commands |
|------|---------|----------|
| 0 | success | all |
| 1 | gate triggered | `parse` (`--fail-on`, `--strict`), `cases boundary` (a case failed), `replay` (a case failed), `ticket --strict` (unmapped ticket) |
| 2 | usage or input error | all (`gen`, `parse`, `cases *`, `replay`, `record`, `ticket`; `adas_analysis` uses 0 / 2) |

`record` and `cases regression` never return 1.

## 11. Troubleshooting

| Message / symptom | Cause and fix |
|-------------------|---------------|
| `error: input file not found: <path>` (exit 2) | wrong path for `parse` / `record --input`; paths are relative to the current directory |
| `error: log file not found` / `anomalies file not found` / `... is not valid JSON` / `invalid anomalies file: ...` | `cases regression` inputs missing or not produced by `parse` |
| `error: manifest not found: <path>` / `invalid manifest: ...` (rule id mismatch, bad window, source outside the manifest directory) | wrong `replay --manifest`; produce it with `cases regression` |
| `error: invalid filter "x": expected module=<ACC\|APA\|HMI\|LKA>` | `--filter` syntax |
| `error: invalid config: ...` | config file missing, not JSON, unknown rule id / key, non-number value |
| `error: scenarios must be an integer >= 8` | `gen` / `record --source live` needs at least 8 scenarios |
| `error: option '--seed <n>' argument '1.5' is invalid. must be an integer` | numeric option type |
| `error: --source file requires --input <jsonl>` / `--input is only valid with --source file` | `record` option combination |
| `error: ticket export not found` / `invalid ticket export: ...` / `duplicate issue key` | `ticket` input |
| `error: missing required argument 'input'` / `required option '--manifest <file>' not specified` | missing argument |
| `error: unknown command '...'` | typo; run `--help` |
| `npm run test:generated` fails on files in `out/reg-*`, `out/tk-*`, `out/tpl-*` | leftovers of older runs of the project's own test suite (current tests clean their scratch directories); delete them: `rm -rf out/reg-* out/tk-* out/tpl-*` |
| Node errors about `.ts` files / unknown flags | Node older than 22.18; check `node --version` |
| `adas_analysis` fails with `error: ... file not found` | run `parse` (and `replay`) first; paths are relative to `analysis/` |
| Dashboard shows an error panel | `public/summary.json` missing or not valid C4 |
| `parse` exits 1 unexpectedly | `--fail-on` / `--strict`; read the summary lines |

## 12. Limitations and gap to production

| Area | This lab | Production would need |
|------|----------|-----------------------|
| Data | seeded synthetic events with injected faults | real recordings (MDF4 / ROS bag / CAN-FD / DLT) and decoders, signal databases (DBC / ARXML) |
| Time | one integer `ts` per scenario, ms, assumed monotonic | clock sync, multiple time bases, wraparound, jitter |
| Rules | 8 rules, hand-written thresholds, no calibration | requirement-traced, calibrated per vehicle variant, reviewed with safety (ISO 26262 / SOTIF) |
| Detection quality | 100% precision / recall measured only against the generator's own labels | field data, false-positive review |
| Collector | in-memory ring buffer, file / simulated live source | on-vehicle logger, storage limits, signing, upload, retention and privacy handling |
| Tickets | synthetic Jira export, label + component mapping | real Jira API, workflows, permissions |
| Scale | tested to 100k events < 5 s, streaming parser | distributed storage and processing |
| Analysis / dashboard | single-file summary, static page | persistent store, auth, drill-down to clips |
| Security | no authentication, no input signing | access control, integrity checks |

Treat results as a demonstration of the tooling approach, not as ADAS validation evidence.
